# 卡牌效果测试方法与本次复盘

本次工作的核心是把牌效拆成能通过实际游戏操作验证的状态变化，再用模型记录和录像共同验收。条目、执行结果和视频分别记录；条目写了某个分支，不等于已经执行过。

## 1. 从牌效写预期，再检查实现入口

先读取当前牌效、基础与升级差异、相关牌的实际定义，再逐项写出预期。源码用于寻找触发入口、观察位置和可能的交互，不能把实现的当前输出直接当作正确答案。牌效没有说明的边界应标记待明确。

|拆解项|要确定的内容|本次例子|
|---|---|---|
|触发时点|打出时、打出后、回合开始、结束或胜利|舞台少女心得安装时不检索，从之后的回合开始触发|
|触发条件|哪些操作满足，哪些相近操作不满足|渴望对照1费防御与0费戒备；同时记录显示费用和实际支付|
|候选与选择|在哪个牌堆、哪类实际对象、选几个、是否随机|知识→飞矢→闪耀轮换；随机加速每次只选一支有效飞矢|
|数量与资源|费用、伤害、回合数、发牌数量及版本|两层渴望各减1；两层故事收益生成两个独立实际对象|
|状态转移|原牌去哪、是否复制、升级和闪耀是否保留|心得移动所选原牌；引弦完成后被上弦放回手牌|
|生命周期|跨回合是否继续、何时重置、叠加是否独立|错开安装两张心得，各自保存不同轮换进度|
|玩家可见结果|牌面、动画、提示、计数与界面先后顺序|故事展示→飞入牌组→计数完成→普通掉落|
|配合与边界|其他牌改变费用、次数、目标或去向时怎样结算|天候降费后打出掌舵；加速＋渴望让引弦完成并耗尽|

每条场景至少写清：准备状态、合法操作顺序、每一步预期、实际记录、执行层级、证据文件和仍缺的分支。不要只复述一次牌效，或写一句“检查持续触发、边界与配合”。

## 2. 按正常、对照、边界和组合扩展场景

先跑最短的正常流程，然后改变一个条件作对照。持续或计数牌必须跨过真正的回合边界；延迟结算必须走到完成，不能只检查安装成功。

- **正常与阴性对照**：渴望安装不推进已有飞矢；1费防御不触发；0费戒备使3→2。
- **重复与跨回合**：同回合连续三次0费，每次只加速一支；真实下回合分开记录自然倒计时和新0费牌触发。
- **缺少对象与容量**：心得知识候选缺失仍轮换；满手跳过后，腾出位置再验飞矢、闪耀阶段。
- **独立叠加**：两张心得错开安装，随后观察“飞矢/知识、闪耀/飞矢、知识/闪耀”；不能仅看能力图标数量。
- **完成与去向**：引弦2→1→0，只命中一次18伤害；上弦回手与加速耗尽分别验证原牌的最终去处。
- **真实配合**：由天候把掌舵3费降到0，再合法打出触发渴望；不在录制中用命令直接改费用。
- **显示边界**：故事六层发放验证超过五张时的散开布局；没有收益时不产生预览或飞牌。

随机场景检查“对象来自实际候选、每次选择数量正确、变化量正确”，不要求随机结果轮流出现。本次恰好选中了三支不同飞矢，这是一次实际结果。

## 3. 分清证据层级

|层级|能支持的结论|本次处理|
|---|---|---|
|源码核对|存在怎样的调用和条件|绝美的凋零开局入口仅做此层核对，未计作真实开局实测|
|钩子级检查|给定状态下，指定钩子的规则输出|旧心得通过改回合号、直接调用钩子检查循环，保留为此层结果|
|原生流程检查|真实出牌、支付、敌方行动、抽牌或胜利链条中的行为|新心得走25次真实回合转换；故事用实际攻击赢下战斗|
|视觉验收|玩家能否看到相应展示、动画、计数和顺序|原片与关键帧核对；动画事件记录作补充|

模型正确和画面正确需要分别验证。故事最初的64项检查证明直接入永久牌组且不进掉落，却没有证明“塞牌动画存在”。用户指出后，新增真实预览、飞牌和计数完成断言，旧实现确实以预览0/预期1失败，再修复并验证。

## 4. 准备环境和观察实际事件

本次使用隔离工作树和隔离Beta实例，随机端口、满解锁、最小化、静默本机输出，录像保留内部游戏混音。操作前先读STS2 MCP文档。录制前准备好牌、生命和场景；录制中只使用原生悬停、出牌、选牌、结束回合等操作。

观察器记录实际对象和原生事件，不替换选择结果，不推进回合号，不模拟受测能力钩子，不设置随机结果。记录重点包括：

- 牌的实际身份、所在牌堆、升级、闪耀预算，以及其他牌的相对顺序。
- 自然抽牌事件与直接移牌的区别，避免把检索当作抽牌验收。
- 每次加速的来源能力、实际支付值、候选、选中对象、前后倒计时和完成状态。
- 胜利前后永久牌组、额外掉落、实际普通奖励候选、原生保存结果。
- 预览是否真的创建、飞牌是否真的创建、完成任务是否结束，以及计数完成通知是否发生。

等待条件也要匹配游戏语义：等出牌完成、实际对象离手、加速结束或下一回合状态到达。固定的短睡眠不能代替这些条件。本次脚本曾因未等出牌完成而只腾出五个手牌位置；重复准备也曾误读旧快照，后来分别用完成条件和唯一场景编号修正。

另一个错误是等待“两份能力＝两个图标”。同名能力会合并显示，正确验证应看两份来源在后续操作中是否分别结算。对于“没有某种奖励”的检查，还要确认实际普通奖励候选非空，防止空集合误通过。

## 5. 失败基线、录像与交付

发现问题后先留下能失败的最小场景，用同一检查验证修复。故事动画的失败基线同时保留了“永久牌组+1”和“预览0、飞入0、计数完成0”，从而准确区分数据发放与视觉缺口。

录像只保留每张牌的主要结算。原片保留原生操作；合辑可添加场景标题并记录编辑方式，不能用剪辑制造跨回合或改变结算先后。编码完成、掉帧0与画面验收分别检查。本次按关键帧复核了牌面、加速、命中、回手/耗尽和飞入牌组等结果。

交付时关联运行版本与程序集哈希、场景编号、前后快照、预期/实际、录制回执、原片、合辑和安装包。先将必要内容保存在原仓库交付目录，再清理临时环境；清理前核对哈希，避免删掉唯一证据。
