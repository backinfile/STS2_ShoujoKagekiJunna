# 去寻找故事吧：胜利后直接加入牌组

用户要求：`去寻找故事吧 战斗结束时直接塞牌组中即可，不要进入掉落`。

## 首轮直接入牌组核对

`CatalogPower.Install` 每次安装登记一张待发故事，`JunnaCombatHooks.AfterCombatVictory` 调用 `KnowledgeProgress.WonCombat`。故事通过原生 `CardPileCmd.Add(..., PileType.Deck)` 直接加入永久牌组，沿单张发放范围处理，不创建额外掉落奖励。

本轮对源码、本地已安装程序集与隔离 Beta 实机的核对一致，当时运行实现已符合直接入牌组的要求，因此该轮没有修改牌效代码；该轮未覆盖塞牌动画。掉落界面的“将一张牌添加到你的牌组”是普通选牌奖励；故事在领取任何掉落前已经加入牌组。

## 按实际效果拆解的操作与预期

录制前清除干扰能力，准备能力牌和最后一击，将敌人生命降到1；测试开始后只用游戏合法出牌完成安装和胜利。每个场景分别经过一次原生战斗胜利，不直接调用 `WonCombat`，不使用测试模式的自动领奖。

|场景|实际操作|胜利前预期|胜利后、领取任何掉落前预期|结果|
|---|---|---|---|---|
|基础|打出1张基础能力，再打出攻击击败全部敌人|安装不立即加故事|永久牌组+1张基础故事，实际目的地Deck；无额外故事掉落|16项通过|
|升级|打出1张升级能力，再正常获胜|同上|仍为1张基础故事，闪耀3/3|16项通过|
|重复安装|合法打出2张能力，再正常获胜|安装不立即加故事|永久牌组+2张故事，两个独立实际对象，各闪耀3/3|16项通过|
|未安装对照|前一场胜利后进入新战斗，不安装能力，正常获胜|牌组无额外变化|不新增故事，不重复发放上一场收益|16项通过|

每场同时检查：胜利发放调用仅完成一次；故事确为本局永久牌组的实际牌；已有牌保留；来源升级不把故事变为升级版；没有创建额外战斗奖励；所有卡牌奖励中无故事；普通掉落仍正常出现；每场实际观察到3张普通奖励候选，确认“没有故事奖励”的检查并非空集合通过。

四场共64项检查通过。另核对最后一场胜利后的原生 `current_run.save`：实际永久牌组15张，含5张故事，所有故事的永久闪耀预算均为3，与胜利后观察状态一致。测试开始时已有1张故事，四场本轮合计新增4张。

## 复现与证据

观察模组为 `tests/StoryDirectDeck/NativeVictoryProbe.cs`，执行脚本为 `tests/StoryDirectDeck/run-native-victory.py`。模组只在准备阶段修改环境；胜利发放、额外奖励和奖励卡的补丁均为观察，不替换结果。

先在隔离实例中进入或继续单人战斗；脚本从已有对局执行。沿隔离启动流程以 `-Port 0` 获取随机端口，使用满解锁、最小化和静默设置。启动前将 `JUNNA_STORY_OUTPUT` 设为结果目录，将测试DLL与JSON清单装入隔离实例mods目录。

```powershell
dotnet build tests/StoryDirectDeck/StoryDirectDeck.csproj -c Release -p:CoreApiPath=<Core API DLL> -p:JunnaAssemblyPath=<Junna Beta DLL>
python tests/StoryDirectDeck/run-native-victory.py --port <隔离端口> --output-dir <观察输出目录> --record
```

本轮环境为 Beta 0.111.0、BaseLib 3.4.7、Core 1.6.0、Junna运行提交 f28e7a3。证据保存在 `artifacts/task-deliverables/story-direct-deck-20261111/`：8.2秒基础版主要结算录像、4份胜利后实际状态、掉落列表、64项结果、存档核对和运行程序集哈希。
